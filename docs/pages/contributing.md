# Contributing {#contributing}

## AI-assisted development {#ai-assisted-development}

If you use an AI coding agent to contribute to MCR, start at the repository root and ask it to read [`AGENTS.md`](https://github.com/cenfun/monocart-coverage-reports/blob/main/AGENTS.md) before making changes. This file is the repository's guide for AI coding agents, regardless of which tool you use. It explains where to find the relevant source and tests, which checks to run, and which commands or generated files require special care.

Give the agent a clear task and expected outcome. Ask it to keep changes focused and report what it actually verified. Review the diff and check results before submitting a pull request.

`AGENTS.md` is for developing MCR itself. To use MCR in another project with an agent, see the [AI agent skill](/pages/ai-agent-skill).

## Source formatting and safety {#formatting-and-safety}

Preserve UTF-8 and LF line endings, as required by `.gitattributes`. LF and CRLF use different numbers of characters, changing source lengths and coverage range offsets. As a result, coverage reports generated by `npm run test` can have different `bytes` values across operating systems, causing coverage snapshot checks to fail even when the code logic is unchanged.

`npm run eol` is intended to repair inconsistent line endings in an existing checkout by rebuilding the Git index and checking out tracked files again according to the repository’s line-ending rules. If a snapshot fails because of line endings, normalize the checkout rather than updating the snapshot baseline to accept the difference.

::: danger Destructive repair command
`npm run eol` runs `git rm -rf --cached . && git reset --hard HEAD`. It clears staged changes and discards uncommitted changes to tracked files. Commit or back up your work before considering this repair. Do not use it as a routine validation or formatting command.
:::

## Documentation and report site {#documentation-and-report-site}

`docs/` contains tracked VitePress source. Keep English and `zh/` page filenames aligned and update both languages for behavior changes.

Keep migration guides versioned as `docs/pages/migration-to-<major>.md` and `docs/zh/pages/migration-to-<major>.md`, preserving earlier guides when adding a new major version. Add the filename stem `migration-to-<major>` to the `migrations` group in `docs/.vitepress/pages.js`. The public URLs are `/pages/migration-to-<major>.html` and `/zh/pages/migration-to-<major>.html`. English `docs/pages/migration-to-*.md` guides are included in the npm package automatically.

## Homepage adopters {#homepage-adopters}

Run `npm run who` to preview the **Who uses MCR** list in `.temp/who/results.json`. Run `npm run who -- --write` to save the candidate pool to `scripts/who/who.pool.json` and the verified list to `scripts/who/who.filterred.json`, which the homepage reads. Add `--refresh` to bypass cached responses. For candidates without manually reviewed evidence, the script looks for `monocart-coverage-reports` in the `dependencies`, `devDependencies`, or `optionalDependencies` of any `package.json` on the default branch. The manifest can be at the root or in a subdirectory; no `mcr` npm script is required.

The command follows both GitHub Dependents tabs to the end of their public pagination, deduplicates repositories, and ranks them by the stars shown in those rows. The report records both the published totals and the visible row counts: the totals in the GitHub header can be larger than what GitHub exposes through pagination.

The pool includes only repositories with more than 1,000 GitHub stars. The command checks their GitHub repository status and skips forks, archived repositories, and candidates whose status cannot be verified.

Usage verification runs only on the resulting pool. It filters out repositories owned by `cenfun`, repositories already listed under **Integrate with MCR**, and candidates without evidence of MCR use on their default branch. For new candidates, the command looks for a declared MCR dependency and an `mcr` command in the root `package.json`. Maintain [`scripts/who/who.sources.js`](https://github.com/cenfun/monocart-coverage-reports/blob/main/scripts/who/who.sources.js) for reviewed source files and manual overrides. Overrides do not bypass the pool, verification, or Star order. Homepage cards link to repositories; each entry also records the usage file for later review. Each card uses the GitHub avatar of the repository owner, as on the Thanks page. The command records the avatar URL automatically.

## Documentation linting {#documentation-linting}

`npm run lint:docs` automatically fixes lint issues using ESLint directly for the VitePress configuration and Vue theme in `docs/`, plus JavaScript code fences in documentation and `README.md`. The official `@eslint/markdown` processor maps diagnostics and fixes back to the Markdown source. `js`, `javascript`, `mjs` and `cjs` fences support the project's syntax/style rules, including VitePress annotations such as `js{1,3-5}:line-numbers` and code-group filenames. Only `no-undef` and `no-unused-vars` are disabled for snippets that omit surrounding context; other correctness rules remain enabled. TypeScript (`ts`) and text fences are not checked as JavaScript. Markdown prose is not reformatted.

For intentionally nonstandard syntax demonstrations, keep `js` highlighting and place `<!-- eslint-skip -->` immediately before that code fence. It skips only that example, including during autofix; repeat the comment for each intentional exception. Do not use JavaScript `eslint-disable` comments to hide errors in normal examples. VSCode's ESLint integration validates Markdown and supports formatting/code fixes with the checked-in editor settings.

```sh
npm run lint:docs             # Check and automatically fix
npm run lint:docs -- --no-fix # Check only (also used by docs)
```

## Generated output and reports {#generated-output}

All documentation output stays under `.temp/`: `.temp/site/` is the published site, `.temp/vitepress-cache/` holds caches, and `.temp/vitepress-ssr/` holds intermediate SSR files. Integration tests write directly to `.temp/site/reports/`; the demo list is maintained as the VitePress pages `docs/pages/examples.md` and `docs/zh/pages/examples.md`, with direct links to reports. All report HTML, data and asset URLs use `/monocart-coverage-reports/reports/`; old URLs are not supported.

`npm run docs:dev` serves existing reports directly from `.temp/site/reports/`, without modifying their HTML or scripts. The **Report Examples** page renders without reports. Run the corresponding repository tests before opening individual reports locally. Missing reports return a 404 with these instructions; the development server does not run tests automatically.

## Cleanup and publishing {#cleanup-and-publishing}

`npm run docs:build` (also used by `docs`) removes previous site output except `reports/` before building, so obsolete pages, legacy report redirects and hashed assets do not accumulate. Integration test groups (`test-node`, `test-browser`, `test-all`) remove marked legacy report redirect directories from the site root while preserving documentation and existing reports; each generated report cleans its own output directory. Reports and raw merge inputs under `reports/` are not globally cleared by either workflow.

For a completely fresh local site, clean only the dedicated `.temp/site/` output, then rebuild documentation and regenerate the required reports. Never clean or generate over `docs/`. CI builds documentation and reports separately, then downloads them into the same site directory for publishing.
