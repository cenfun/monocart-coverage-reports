# V8 collection {#v8-collection}

## Step 1: Prepare the build {#build}

If your source code is compiled or bundled, enable sourcemaps in your build tool so runtime coverage can be mapped back to the original source. Disabling minification and tree shaking is recommended to simplify coverage debugging and retain code you want to measure.

- [webpack](https://webpack.js.org/configuration/): `devtool: 'source-map'` and `mode: 'development'`; see [webpack.config-v8.js](https://github.com/cenfun/monocart-coverage-reports/blob/main/test/build/webpack.config-v8.js).
- [rollup](https://rollupjs.org/configuration/): `sourcemap: true` and `treeshake: false`.
- [esbuild](https://esbuild.github.io/api/): `sourcemap: true`, `treeShaking: false`, and `minify: false`.
- [vite](https://vitejs.dev/config/build-options.html): `sourcemap: true` and `minify: false`.

Keep the original sources, generated files, and sourcemaps from the exact build used in your tests. See [Sourcemaps and debugging](/troubleshooting/sourcemaps) for details.

## Step 2: Collect coverage {#collect}

Choose one of the following three approaches based on your runtime and integration.

### 1. Browser {#browser}

Native V8 coverage collection in browsers is supported only in Chromium-based browsers. Use a browser automation tool to start collection before your tests and retrieve JavaScript and CSS coverage afterward:

#### Playwright {#playwright}

Here, `page` is an existing [Playwright Chromium page](https://playwright.dev/docs/library#usage). Replace `your page url` with the tested page URL, and run and await your test actions after navigation and before stopping coverage.

```js
await Promise.all([
    page.coverage.startJSCoverage({
        // reportAnonymousScripts: true,
        resetOnNavigation: false
    }),
    page.coverage.startCSSCoverage({
        // Note, anonymous styles (without sourceURLs) are not supported, alternatively, you can use CDPClient
        resetOnNavigation: false
    })
]);

await page.goto('your page url');

const [jsCoverage, cssCoverage] = await Promise.all([
    page.coverage.stopJSCoverage(),
    page.coverage.stopCSSCoverage()
]);

const coverageData = [... jsCoverage, ... cssCoverage];

```
For Playwright Test automatic fixtures, see [fixtures.js](https://github.com/cenfun/playwright-coverage/blob/main/fixtures.js) in the complete [playwright-coverage example](https://github.com/cenfun/playwright-coverage). The [best-practices guide](https://github.com/cenfun/monocart-coverage-reports/blob/main/skills/monocart-coverage-reports/references/best-practices.md#complete-project-example) explains the integration.
For more examples, see [./test/test-v8.js](https://github.com/cenfun/monocart-coverage-reports/blob/main/test/test-v8.js), [css](https://github.com/cenfun/monocart-coverage-reports/blob/main/test/test-css.js)

For more integration examples, see [Playwright](/integrations/frameworks-and-tools#playwright).

#### Puppeteer {#puppeteer}

Here, `page` is a Puppeteer page, not the Playwright page object above; see the browser and page initialization in the [Puppeteer example](/reference/cdp-client#puppeteer). Replace `your page url` with the tested page URL, and run and await your test actions after navigation and before stopping coverage.

Use Puppeteer’s coverage API with `includeRawScriptCoverage: true` to retrieve native V8 script coverage, then combine it with the collected CSS coverage as shown below.

> Depending on your package manager, Puppeteer may not download a browser during installation. If no browser is available, install one manually:
>
> ```sh
> npx puppeteer browsers install chrome
> ```

```js
await Promise.all([
    page.coverage.startJSCoverage({
        // reportAnonymousScripts: true,
        resetOnNavigation: false,
        // provide raw v8 coverage data
        includeRawScriptCoverage: true
    }),
    page.coverage.startCSSCoverage({
        resetOnNavigation: false
    })
]);

await page.goto('your page url');

const [jsCoverage, cssCoverage] = await Promise.all([
    page.coverage.stopJSCoverage(),
    page.coverage.stopCSSCoverage()
]);

// to raw V8 script coverage
const coverageData = [... jsCoverage.map((it) => {
    return {
        source: it.text,
        ... it.rawScriptCoverage
    };
}), ... cssCoverage];
```
Example: [./test/test-puppeteer.js](https://github.com/cenfun/monocart-coverage-reports/blob/main/test/test-puppeteer.js)

For more integration examples, see [Puppeteer](/integrations/frameworks-and-tools#puppeteer).

### 2. Node.js {#nodejs}

::: tip Recommended for most users: the CLI
- [`mcr`](/reference/cli#command-line): collect coverage for an existing Node.js script or test command.
- [`mcr test`](/getting-started/node-test-runner#quick-start): run tests with Node.js's built-in test runner and collect coverage.

The CLI wraps Node.js's native coverage collection workflow, automatically retrieving data and generating reports without manually setting `NODE_V8_COVERAGE` or writing collection code.
:::

The approaches below use lower-level Node.js capabilities. They are intended for developers building custom collection workflows or integrations; most users do not need to configure them individually:

- [NODE_V8_COVERAGE](https://nodejs.org/docs/latest/api/cli.html#node_v8_coveragedir)=`dir`
    - Sets Node.js env `NODE_V8_COVERAGE`=`dir` before the program running, the coverage data will be saved to the `dir` after the program exits gracefully.
    - Read the JSON file(s) from the `dir` and generate coverage report.
    - Example:
    > cross-env NODE_V8_COVERAGE=`.temp/v8-coverage-env` node [./test/test-node-env.js](https://github.com/cenfun/monocart-coverage-reports/blob/main/test/test-node-env.js) && node [./test/generate-report.js](https://github.com/cenfun/monocart-coverage-reports/blob/main/test/generate-report.js)

- [V8](https://nodejs.org/docs/latest/api/v8.html#v8takecoverage) API + NODE_V8_COVERAGE
    - Writing the coverage started by NODE_V8_COVERAGE to disk on demand with `v8.takeCoverage()`, it does not require waiting until the program exits gracefully.
    - Example:
    > cross-env NODE_V8_COVERAGE=`.temp/v8-coverage-api` node [./test/test-node-api.js](https://github.com/cenfun/monocart-coverage-reports/blob/main/test/test-node-api.js)

- [Inspector](https://nodejs.org/docs/latest/api/inspector.html) API
   - Connecting to the V8 inspector and enable V8 coverage.
   - Taking coverage data and adding it to the report.
   - Example:
   > node [./test/test-node-ins.js](https://github.com/cenfun/monocart-coverage-reports/blob/main/test/test-node-ins.js)
   - vm Example (scriptOffset):
   > node [./test/test-node-vm.js](https://github.com/cenfun/monocart-coverage-reports/blob/main/test/test-node-vm.js)

- [CDP](https://chromedevtools.github.io/devtools-protocol/) API
    - Enabling [Node Debugging](https://nodejs.org/en/guides/debugging-getting-started/).
    - Collecting coverage data with CDP API.
    - Example:
    > node --inspect=9229 [./test/test-node-cdp.js](https://github.com/cenfun/monocart-coverage-reports/blob/main/test/test-node-cdp.js)

- [Node Debugging](https://nodejs.org/en/guides/debugging-getting-started) + CDP + NODE_V8_COVERAGE + V8 API
    - When the program starts a server, it will not exit on its own, thus requiring a manual invocation of the `v8.takeCoverage()` interface to manually collect coverage data. Remote invocation of the `v8.takeCoverage()` interface can be accomplished through the `Runtime.evaluate` of the CDP.
    - Example for [koa](https://github.com/koajs/koa) web server:
    > node [./test/test-node-koa.js](https://github.com/cenfun/monocart-coverage-reports/blob/main/test/test-node-koa.js)

- [Child Process](https://nodejs.org/docs/latest/api/child_process.html) + NODE_V8_COVERAGE
    - see [Command Line](/reference/cli#command-line)

### 3. General-purpose CDP {#cdp}

The [Chrome DevTools Protocol (CDP)](https://chromedevtools.github.io/devtools-protocol/) can connect to a Node.js process or Chromium browser with debugging enabled. MCR provides `CDPClient` to start and stop collection and retrieve coverage through a debugging port or an existing CDP session.

See [CDPClient](/reference/cdp-client#cdpclient) for integration details and examples.

## Step 3: Generate a report {#generate}

Pass `coverageData` from the browser or CDP examples above to the [quick-start API example](/getting-started/get-started#api) to generate reports. That example also explains the input, returned result and their types.

If you collected files with `NODE_V8_COVERAGE`, run the reporting script after the tested process exits and **replace** `await mcr.add(coverageData)` in the API example with:

```js
await mcr.addFromDir('./v8-coverage');
```

Here, `./v8-coverage` must be the directory used for `NODE_V8_COVERAGE` during collection. Preserve matching tested sources and sourcemaps, and keep it separate from report output. This is different from an MCR `raw` directory for [merging reports](/reference/merging#manual-merging), which is loaded through `inputDir`.

MCR's register hook retains the `source-<hash>.json` filename format. The hash includes the process ID, worker thread ID and process start time; these execution fields are also stored in the JSON content for association. Here, `execution.timestamp` is the process start time in epoch milliseconds, not the snapshot write time encoded in Node's coverage filename. `addFromDir()` uses a single captured source directly. Only when a URL has multiple candidates does it use Node's original coverage filename to select the best execution match, so separate processes and workers can share a collection directory even when they load different source versions at the same URL. Repeated executions of identical sources still merge normally. The same association applies when `generate()` loads [`dataDir`](/reference/options#datadir). When copying a collection directory, preserve Node's original `coverage-*.json` filenames and the execution metadata in `source-*.json`. Source execution identity is read from JSON, not parsed from source filenames.

Older captures without execution metadata remain readable. For every URL with captured sources, MCR always selects one source without emitting an association warning: it prefers the matching process and thread with the latest process-start timestamp no later than the snapshot. If there is no execution match, it prefers legacy captures without execution metadata, or otherwise falls back to all candidates. Remaining ties use the first candidate in source-filename order. This deterministic fallback is best-effort: incomplete metadata or different builds loaded at the same URL within one live process and thread can still make coverage for that URL inaccurate. Recollect with the current register hook and run different builds in separate processes for reliable results. Uncaptured files still require the exact tested source and sourcemaps. For independent machines or archived builds, keep collection directories separate and call `addFromDir()` for each, or export MCR [raw reports](/reference/merging#manual-merging).

Close any browser you created after collection; see [CDPClient](/reference/cdp-client#generate) for custom client cleanup.
